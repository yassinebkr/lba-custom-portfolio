**Baseline:** The maintainer imported a locally built 10,131,360-byte GOG-derived .jsdos archive through the GitHub Pages js-dos 6.22 loader on 2026-11-13 and reported that the game started successfully. This is owner-reported manual evidence, independent of the synthetic CI. Keep the commercial ZIP and all original game resources private.

**Scope and precedence:** stabilize audio, targeted scene loading and game-over recovery before starting R06 art improvements. Character/prop/scene visual quality must pass the artistic gates before creating a general cinematic authoring pipeline. The public launcher design needs redesign; retain its working import behavior until a separate visual review.

## Audio diagnosis before any driver change

`LBA.CFG` generated by `scripts/runtime/build-private-jsdos.py` deliberately disables wave, mixer and MIDI. The archived game binaries can boot, but Sound Blaster hardware emulation alone cannot make the original DOS executable produce audio.

In the published original [ADELINE.C](https://github.com/LBALab/lba1-classic-community/blob/main/LIB386/LIB_SYS/ADELINE.C), the engine calls `WaveInitDLL(WaveDriver)`. The DOS [WAVE.C](https://github.com/LBALab/lba1-classic-community/blob/main/LIB386/PLATFORM/DOS/LIB_SAMP/WAVE.C) loads the named driver file and fails initialization if it is absent. The historic docs do not establish that GOG's `Speedrun/Windows/` folder contains this binary. A made-up `WaveDriver: SB16` setting is unsafe.

Check the actual GOG installation **read-only** (no Windows NVMe access):

~~~bash
cd ~/Documents/lba-custom-portfolio
git pull --ff-only
BASE=/mnt/fast-ssd/Games/Heroic/tlba-classic/Speedrun/Windows
python3 scripts/runtime/audit-dos-install.py --base "$BASE"
~~~

The diagnostic prints only resource names, `LBA.CFG` audio settings and installed driver filenames. The private builder supports `--audio off` (the known working baseline), experimental `--audio source-wave` and guarded `--audio sb16`. The source-wave mode requires `LBA.CFG` to name an installed DOS wave DLL, `WaveExec=NoExec`, port 220h, IRQ 7, DMA 1 and a checked sample rate. The `sb16` mode is an independent experiment using the owner-supplied `W_SB16.DLL` at the same 220h/IRQ7/DMA1 settings even if the source configuration disables audio. If the local DOS DLL is missing or has an unexpected size, the SB16 builder fails closed. MIDI and mixer remain disabled; successful packaging does not prove sound.

**Audio validation sequence:** first prove that a real wave DLL is available; then create separate baseline and wave-enabled private ZIPs; test SFX in the same scene and compare startup, responsiveness and browser errors. Music and voices require separate backends, asset sizes and test gates. The presence of `SAMPLES.HQR` alone does not prove that effects are audible.

## Controlled scene-loading test using recovered saves

The legacy generator already defines `museum`, `house`, `citadel`, `old_burg`, `proxima`, `rebellion` and `harbor`. It emits DOS slots such as `S003.LBA` for `museum`. Preserve the game installation and create the saved state in the ignored project output:

~~~bash
cd ~/Documents/lba-custom-portfolio
node scripts/hqr-tools/create-savegame.js list
node scripts/hqr-tools/create-savegame.js museum --dos --no-deploy
python3 scripts/runtime/build-private-jsdos.py \
  --base /mnt/fast-ssd/Games/Heroic/tlba-classic/Speedrun/Windows \
  --mods ./output/r05-empty \
  --saves-dir ./output/saves/dos \
  --audio off \
  --out ./web_deploy/lba1_museum_probe.jsdos
~~~

Select the **newly built** local file at the [GitHub Pages js-dos loader](https://yassinebkr.github.io/lba-custom-portfolio/web_deploy/). Try the game's *Continue Saved Game* menu and select `Museum`. Confirm that Twinsen appears in the intended room, does not fall through geometry, can walk, and survives transitions. Existing slots are copied to the ZIP root unchanged.

If the game does not offer the save or loads incorrectly, record the menu state and scene. Do not implement an automatic boot patch until the save-file route has been verified in the real original executable.

An automatic start without selecting a save may require a compatible engine-level change; putting `S003.LBA` in a ZIP **does not** by itself auto-load that scene.

## Reproducing and isolating the black screen on death

The owner reports a black screen after death. Original code enters `GameOver()` after the last life, draws a `RESS_GAME_OVER` 3D object and eventually returns. The sequence also calls a sample numbered 37. Test reproducibly before trying to fix it.

1. Run the known-good *audio off* ZIP. Take a screenshot immediately before death and one after the screen goes black.
2. Distinguish loss of a single life (clover respawn) from a final game over. Check if the browser canvas remains responsive after at least 15 seconds and try ESC.
3. Repeat with the museum save if it loads, to isolate scene-specific life scripts.
4. Capture the browser console and approximate delay. Compare a clean native DOSBox run using the *same* private game files if available.
5. Only after reproduction, trace `GameOver()` transitions, `RESS_GAME_OVER` extraction, palette restoration, and sample 37.

A safe reload from the public launcher is a recovery workaround, **not** a fix to the game-over bug.

### Opt-in browser evidence for black-screen after death

Use the updated launcher from this branch locally (the published Pages page
is not updated until an explicitly approved deployment). This preserves
the existing import flow and adds no new visible UI:

~~~bash
cd ~/Documents/lba-custom-portfolio/web_deploy
python3 -m http.server 8765
# Open http://localhost:8765/?r05debug=1
~~~

Import the silent control bundle. In DevTools, run this before death and
again after a black screen (press ESC once and capture a third snapshot):

~~~js
copy(JSON.stringify(window.lbaR05DiagnosticReport(), null, 2));
~~~

Record separately (1) life loss with an available four-leaf clover and
(2) terminal game over with no remaining clovers. Capture screenshots,
time since death, and whether ESC or the main menu responds after at
least 15 seconds. Then repeat with the wave candidate if it was packaged.
Use identical saves and the same test scene in both runs.

The browser report includes import/launch milestones, window errors,
unhandled promise rejections, canvas visibility and focus; it contains no
game files or keystrokes. **It does not inspect DOS CPU execution, TimerRef,
framebuffer updates or the guest program counter.** A black frame with no
browser error therefore cannot establish that the guest engine is alive.

In the community game source, GameOver() uses a 3D model from RESS.HQR,
sample 37 and TimerRef-dependent loops, followed by a display transition.
There is no direct FLA playback in this routine. In-game recovery therefore
requires evidence about this specific path before patching the executable.


### November 2026: verified driver family, separate SB16 test

The historical game supports a Sound Blaster 16 FX profile. A file inventory
for the Windows Speedrunner distribution lists W_SB16.DLL, and the
lba1-classic-community compilation guide also names W_SB16.DLL as the wave
driver. The presence of that file on the owner's particular GOG installation
must be checked rather than inferred from a storefront listing.

References:
- https://steamdb.info/depot/397332/history/
- https://lba-classic-doc.readthedocs.io/en/latest/lba1/compile.html
- https://github.com/mitigd/lba-hle/blob/main/docs/project.md

The runner now builds a silent control and attempts source-wave and SB16
experiments independently. Depending on the actual local GOG files, it creates
one, two or three .jsdos bundles under output/r05-probes/. Compare the same
save slot and action in the silent control and any enabled-audio candidate.
The test driver in synthetic CI is intentionally non-working; only the
manual browser test can confirm audible SFX.

The report includes read-only structural checks for RESS.HQR index 21
(GameOver 3D model) and SAMPLES.HQR index 37 (game-over sample), using
the original sources' index-table and entry-header layout. Run the standalone
inspection on the owner-provided GOG directory:

~~~bash
python3 scripts/runtime/inspect_gameover_resources.py --base "$BASE"
~~~

A result marked present means the entry is within HQR bounds with a supported
compression method, not that its decoded payload is semantically valid.
A missing or invalid entry is a concrete lead; a present entry leaves palette,
timer, model decoding and the game transition to investigate.
